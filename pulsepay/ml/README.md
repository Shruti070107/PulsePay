# PulsePay Machine Learning Anomaly Detection Service

This service implements unsupervised statistical anomaly detection on payment transactions to capture unusual operational footprints.

## Why Isolation Forest?
We use `sklearn.ensemble.IsolationForest` because:
1. **Unsupervised Nature**: Payment incidents and fraud patterns are constantly shifting; we rarely have complete or clean labeled datasets of all failure modes. Isolation Forest fits on unlabeled transactional logs and isolates anomalies.
2. **Explainability & Performance**: It isolates observations by randomly selecting a feature and split value. Anomalies travel down shorter decision paths in trees, making the model fast and computationally lightweight.
3. **Multi-Dimensional Analysis**: Unlike deterministic rules that check individual triggers, Isolation Forest checks feature interactions (e.g. high retry counts combined with an unusually high amount and webhook delays).

## Feature Engineering (11 Features)
The Node.js feature extractor client compiles the following normalized feature vector for each payment:
1. `amount`: Numerical payment value.
2. `processing_time_ms`: Millisecond duration between creation and final state.
3. `webhook_failure_count`: Total delivery failures (HTTP errors).
4. `webhook_retry_count`: Max retry attempt number.
5. `webhook_delay_ms`: Timing offset between gateway capture and first webhook delivery.
6. `event_count`: Total event log count (timeline complexity indicator).
7. `event_order_violation`: Boolean (1.0 or 0.0) indicating out-of-order arrival.
8. `duplicate_similarity`: Boolean (1.0 or 0.0) indicating similar payment attempts within 1 minute.
9. `merchant_failure_rate`: Historical payment failure rate for this merchant.
10. `payment_failure_rate`: Historical overall system failure rate.
11. `hour_of_day`: Creation hour (0–23) to capture timing patterns.

## Training Pipeline
Training data is generated by triggering a MongoDB features scan from the Express API (`POST /api/ml/train`). Features are extracted across all historical database records, and sent to FastAPI to fit the Isolation Forest model. 
The fitted model is serialized and saved to disk at `ml/models/isolation_forest.pkl`.

## Score Interpretation
Scikit-learn's `decision_function` returns raw scores where lower values represent anomalies. We normalize this output to the range `[0.0, 1.0]` for operator visibility:
* `normalized_score = np.clip(0.5 - raw_score, 0.0, 1.0)`
* `0.0` represents a completely normal transaction.
* `1.0` represents a highly anomalous transaction.
* `is_anomaly` is true if the model flags the point (scikit-learn prediction equals `-1`).

## Architectural Boundary
* **No State Decisions**: The ML model does **NOT** make state decisions. It does not declare if a payment was captured or webhooks delivered. These remain deterministic.
* **No Severity Elevators**: An ML anomaly alert alone does **NOT** trigger a high-severity critical incident. It acts as reinforcing evidence to highlight anomalies for manual investigation.
